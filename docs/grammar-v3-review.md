# v3 语法追加评审

评审对象：`docs/granmmerv3.nw` 第 171 行之后（`+=` 分片接线、`book` 保留结构、`nw parse --ast`），以及 209–235 行的 book/part/essay 定稿。

范围：只评审。不改实现、不改 `book/` 书稿、不改原草案。

## 结论先行

1. **方向对。** `+=` 把一次性声明变成可分片累积，和「agent 声明拓扑、程序做综合」的定位一致；book 结构把顺序从 YAML 产物搬回源，weave 不再依赖 tangle，链条短了一环。
2. **还差 6 条语义没定死**，其中 3 条（分片顺序、实例别名、tangle 输入顺序）直接决定产物能否复现。
3. **草案有 6 处自相矛盾或断句。** 199 行那处已口头澄清（top 例外），但正文没改，实现者读到的仍是矛盾。
4. **book/part/essay 已经能用**，剩下要定的是：book 的发现规则、part 的名字作用域与嵌套顺序、essay 是「名字」还是「路径」。
5. **235 行的拍板会让单篇 tangle 消失。** 这条要同步进 CLI、测试与错误信息，否则实现第一天就会撞上。

## 一、必须定死的语义

### 1.1 分片顺序（201 行答非所问）

201 行问「怎么确定追加顺序」，紧接着回答的是跨篇的拓扑序，没有回答**同一对象的多个分片谁先谁后**。

`dir top += dir b;` 写在 A 篇、`dir top += dir c;` 写在 B 篇，若没有一条全序，`b` 与 `c` 的先后取决于文件读入顺序，产物不可复现——这与「diff 要稳定」直接冲突。

建议条文：**分片拼接顺序 = book 先序 → 篇在 book 先序中的位置 → 篇内行号。**

这条之所以有解，正是因为 235 行：不在 book 里的篇不参与装配，所以「篇内行号」永远有定义。

### 1.2 AST 实例别名（54 行）

54 行说「AST 中它有一个独一无二的别名」，但没说怎么生成。`+=` 会让同一个 chunk 被追加多次，AST 必须能稳定区分。

建议：`<file_key>#<接线体序号>.<行号>`。接线体序号在 parse 时按分片顺序递增。要求：可复现、可 diff、与文件读入顺序无关。

### 1.3 `@` 与 `+=` 的唯一区别（199 行 + top 例外）

建议写成一条通则，而不是两套语义：

- `@` 至多一次；
- `+=` 任意次；
- 两者都能创建对象；
- 例外：`top` 必须先 `dir top @`，之后只能 `+=`。

理由：两套语义在「首次」时行为相同，只会在实现里分叉。推论：`defined` 由 `@` 或 `+=` 任一置位；`@` 的第二次出现报错。

### 1.4 tangle 的输入顺序（201 行 + 235 行）

命令行篇序退化为**解析顺序**；装配顺序由 book 先序决定。命令行漏了 book 引用的篇 → error。

需要同步改的说法：

- `nw tangle` 的 usage（篇列表不再是顺序来源，只是输入集合）；
- `Makefile` 里 `find book -name '*.nw' | sort` 的顺序不再有意义，只剩「给全输入」一个作用。

### 1.5 book 的发现规则（211 行）

「全项目只有一个」需要先定**判定范围**：

- 以一次调用的**全部输入文件**为范围（推荐）：parse 完所有输入，book 定义数 ≠ 1 → error；
- 若以某个固定路径为范围，就退回了 `book.yaml` 的老路，和「不需要额外文件」的目标矛盾。

还要定：book 定义的位置不限（写在任何一篇里都行），但建议单独一篇（如 `book/book.nw`），否则「书的结构」会藏在一篇散文中间。

### 1.6 `nw parse` 的输出（205 行）

`nw parse --ast` 输出「最终装配清单」。要定四件事：

- 不带 `--ast` 时输出什么（建议：人读的摘要——dirs/files/chunks 计数 + book 先序，一行一项）；
- `--ast` 的格式（建议 JSON，插件与 weave 都能吃）；
- schema：`{ dirs, files, chunks, book: { name, order: [...] }, instances: [...] }`，其中 `order` 是 essay 的完整先序；
- 输出走 stdout，错误走 stderr。

## 三、`+=` 的边界

### 3.1 糖行的挂载父

`dir top += dir b;` 里 `dir b;` 的父**恒为 `+=` 左侧的 top**。这条要写死，否则 `dir b;` 不知道挂哪。

`part zzz += part sss;` 同理：`sss` 成为 `zzz` 的子 part。

### 3.2 糖的允许表

| 左侧 | 允许的糖 | 等价于 |
|---|---|---|
| dir | `dir X += dir Y;` / `dir X += file<t> Y;` | `dir X += @ dir Y; ~@` |
| file | `file<t> X += << chunk >>;` | `file<t> X += @ << chunk >> ~@` |
| part | `part X += part Y;` / `part X += essay p;` | `part X += @ part Y; ~@` |
| book | `book X += part Y;` / `book X += essay p;` | `book X += @ part Y; ~@` |

糖只允许**单个**目标；多个一律用 `@` 体。

理由：`file X += << a >> | << b >>` 会让「按行追加」与「按体追加」两套语义挤在同一行。草案 193 与 195 行给的正是单目标糖，保持这个边界最省事。

### 3.3 唯一性只约束挂载

「同名同类型只能挂一处」约束的是 dir/file（以及 part）的**挂载**。

chunk 实例是复制语义：`file X += << a >> | << a >>` 合法，`+=` 体里同一块出现两次也合法。

### 3.4 只在结构行生效

`+=` 只在行首是保留字（`dir`/`file`/`book`/`part`）时被识别。

chunk 体内 `x += 1` 是目标语言，不解析——这条与 146 行的注释规则同源：块内是别人的语言，我们只做搬运。

### 3.5 按什么匹配

- dir / part / book：按名字；
- file：按 `(name, type)`，`file<c> x` 与 `file<h> x` 是两个对象；
- essay：按路径字符串（规范化后，见 4.4）。

## 四、book / part / essay 正式规则

### 4.1 对象模型

`book` 是第四类对象，与 dir/file/chunk 不同：**不落盘、不挂载、不参与物理路径**。它是一份清单。

`part` 是清单里的分组节点，`essay` 是清单里的叶子（指向 `.nw`）。

所以物理树（dir/file）与清单树（book/part/essay）是两棵树，唯一的交叉点是 essay 的路径。

### 4.2 规则表

| 项 | 规则 |
|---|---|
| book 数量 | 全项目 1 个；0 个（weave/tangle）→ error；≥2 → error |
| book 名 | 标识符即书名，可中文；`+=` 必须同名，否则按「+= 到不存在的对象」error |
| part 作用域 | 建议全项目唯一（`part sss += …` 不带父名，说明按名字寻址）；重名 → error |
| part 嵌套 | 允许；检测环（`part a += part b;` + `part b += part a;` → error） |
| 顺序 | 容器体内出现顺序 + `+=` 追加顺序；part 递归展开 |
| essay 值 | 仓库根相对的 `.nw` 路径 |
| essay 缺失 | error（217 行「都要能在目录里找到」） |
| essay 重复收录 | error（一篇只能排一处） |
| 未被收录的 `.nw` | 不进 tangle（235 行）；建议 info 提示，不报错 |
| 体内容 | book 体：part 挂载 / essay / `name`；part 体：part 挂载 / essay；essay 是叶子 |
| 保留字 | `book`、`part`、`essay`（另加已有的 `top`/`dir`/`file`） |

### 4.3 顺序：先序深度优先

```
book neoweb @
	part 序;
	essay 前言;
	part 第 1 章;
~@

part 序 @
	essay book/menu.nw;
	part 序的附录;
~@
```

展开：`序` → `book/menu.nw` → `序的附录` 的子项 → `前言` → `第 1 章` 的子项。

规则只有一条：**容器体是一个有序列表，元素是 part 或 essay，按出现顺序展开；part 展开时先展开它的子项（先序）。**

散篇（book 下直接挂的 essay）按它在列表里的位置插进去，不特殊排到末尾。

### 4.4 essay 是名字还是路径

217 行的例子写 `essay xxx;`，看起来像名字；但「都要能在目录里找到」要求它是路径。

建议定成**路径**，例子改成 `essay book/Chapter 1/1-history.nw;`。若坚持用名字，就得再定一条「名字 → .nw 路径」的映射——而那条映射只能来自 `file<md>` 对象或约定，会把两棵树又绑在一起，与 71 行「namespace 与文件/文件夹彻底没关系」的精神相反。

### 4.5 本书迁移样例

把现在的 `tangle/book.yaml` 转写成新语法：

```
book neoweb @
	part 序;
	part 第 1 章 为什么是文学编程;
	part 第 2 章 语法;
	part 第 3 章 实现;
	part 第 4 章 入口;
	part 第 5 章 展开;
	part 第 6 章 协作;
	part 附录 A 构建;
	part 附录 B 示例;
	part 附录 C 编辑器;
	part 附录 D 参考;
~@

part 序 @
	essay book/menu.nw;
	essay book/skeleton.nw;
~@

part 第 1 章 为什么是文学编程 @
	essay book/Chapter 1/1-history.nw;
	essay book/Chapter 1/2-crisis.nw;
	essay book/Chapter 1/3-attempt.nw;
	essay book/Chapter 1/4-decisions.nw;
	essay book/Chapter 1/5-why.nw;
	essay book/Chapter 1/6-outlook.nw;
~@
```

本书没有散篇：每个 `.nw` 都在某个 part 下。`docs/*.nw` 正好验证 235 行——它们不属于书，不进 tangle。

### 4.6 保留字与结构行识别

保留字扩充后，散文里以 `book`/`part`/`essay` 开头的行会被误认成结构行。三条防护：

- 结构行必须符合形状：`X @`、`X += …`、`X name;`（行首关键字 + 空格）；
- 行首不是保留字的一律散文；
- 反引号围栏内不解析（现有规则已覆盖）。

## 五、235 行的后果

### 5.1 单篇 tangle 消失

`nw tangle 一篇.nw` 不再成立：没有 book 定义就没有装配序。

这是 235 行的直接推论，**不是缺陷**，但要写进 CLI 文档与错误信息——报「这本书没有 book 定义」，而不是「输入为空」。

### 5.2 测试与示例

`test_bootstrap.py` 的 27 个用例大多用单文件 tangle，每个都要带一个最小 book：

```
book t @
	essay a.nw;
~@
```

或者给 tangle 留一个 `--no-book` 逃生门。不推荐：那等于把「没被收录也能装配」又放回来，235 行的决定会被绕过。

### 5.3 未被收录的 `.nw`

按 235 行，这是「不属于这本书」的正常状态。建议 info 级提示（本次输入里有 N 篇未收录），不报错。

否则 `docs/*.nw` 这类文件会让每次构建都飘警告。

### 5.4 `-b` 与 `tangle/book.yaml` 退场

- `Options.book` 的默认值 `tangle/book.yaml` 删除；
- `nw weave` 的 `-b` 要么删掉，要么改成「book 定义所在文件」的提示（若发现规则是全输入扫描，就不需要）；
- `book/menu.nw` 从「目录的产物」变成「目录所在的篇」——它仍是一篇，但不再 tangle 出 yaml。

### 5.5 命令行还需要篇列表吗

若 tangle 的输入就是「整本书的所有 `.nw`」，命令行可以只收目录；但保持「收篇列表」更简单，Makefile 已经在找文件。

需要写明：**列表决定解析什么，book 决定装配什么**；两者不一致时以 book 为准，book 引用了未提供的篇 → error。

可直接抄回 `granmmerv3.nw`：

```

  例外：top 必须先 dir top @，之后只能 +=。
```
