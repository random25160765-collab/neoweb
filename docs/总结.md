# 项目总结：文学化编程人机协作工具

## 一、问题

AI 生成的代码速度远超人的理解速度。由此产生四类理解障碍：意图缺失（代码不解释“为什么”）、结构淹没（逻辑散落在大量文件中，看不到主线）、抽象不一致（同一概念多种表达）、修改痕迹不可见（语义变更没有记录）。更深层的问题是**成本外部化**：AI 产出的理解成本被转嫁给了每一个读代码的人，每人重复支付语法展开、模式识别、领域前提的税。传统项目靠“默认知识共享 + 师徒传递”消化这些成本，但在跨栈、AI 大量参与、人员流动快的项目里，这套机制已经失效。

## 二、主张

用文学化编程的 chunk 结构，把人的理解带宽重新对齐到 AI 的代码产量上。工具不解决正确性、不替代测试，它让理解有结构化入口。更进一步：工具是**人与 AI 平等协作的载体**——人写引子，AI 续写，双方在同一叙事空间里交替落笔。传统 IDE 补全失败是因为缺约束；agent 对话框好用但不平等且回合制。文学化编程提供的是**有约束的实时协作**。

## 三、核心判断

1. **从“写作方法”到“协作协议”**：chunk 结构是双方都能读写、可协商的公共对象；chunk 引用图是机器可验证的叙事契约；文档块是 AI 生成时的上下文锚点，也是人 review 的结构化接口。这是旧思想在 AI 时代的内涵和外延扩展。

2. **从“可理解”到“可教学”**：技术能力是幂律分布，99% 的读者不是全栈专家。叙述的默认姿态是“在读者可能卡住的地方主动展开”——语法糖解释、模式命名、领域前提补充。可教学才是在技术栈无限宽的行业里让代码真正被人接住的唯一方式。

3. **成本内部化**：AI 生成代码时同步写下动机和解释，是让生成方为阅读方买单。AI 付得起（token 和时间，可并行、可自动化），人付不起（重复、不可分摊）。

4. **信任基础设施**：人类对 agent 的提防是对不可见过程的提防。文档是 agent 的可见性承诺——信任不是靠 agent 表现得可靠建立的，是靠它让自己变得可检查建立的。

5. **生产和教学重合**：跨栈项目的接缝知识不在任何教程里，只存在于项目的具体实现和设计决策中。能让项目被维护的叙述和能让项目被学会的叙述是同一份东西。

6. **叙述的最低层已足够**：如实转述（消语法税）是底线，且是当前 AI 稳定能产出的。第 2、3 层（约束、意图）是锦上添花。语法糖密度越高，如实转述的 offload 价值越大。

7. **冒险写法需要论证**：纯代码审查下，审查方在信息缺失时只能按最坏假设提防御建议，导致防御代码过度堆积。叙述把冒险的完整论证写下来，审查的层次从“代码是否安全”提升到“论证是否成立”。

8. **与 RLCR 融合**：RLCR 提供独立的外部视角，文学编程提供这个视角可以审视的思维链。审查对象从“代码 diff”扩展到“叙述 + 代码”，问题定位从行级提升到 chunk 级。

## 四、技术决策

**文档语法**：裁剪 LaTeX，向 Markdown 简洁性靠拢。正文 Markdown 风格，数学公式保留 `$...$` / `$$...$$`。

**输出路线**：拒绝 LaTeX 工具链（宏展开调试、包冲突、错误信息不友好的技术债）。weave 输出干净 HTML（语义结构 + KaTeX 公式 + 代码高亮），美观交给自定义 CSS 设计系统；PDF 用 Puppeteer 复用同一套 CSS 的 `@media print`。

**处理器**：parse（状态机分离文档块/代码块）+ tangle（递归展开 chunk 引用 + 环检测）+ weave（输出 HTML）。核心语言无关，语言相关部分（如测试语义）作为可插拔后端。第一版只预留标签，不实现测试语义。

**实现语言**：Rust 或 C++，单进程、整文件读入内存、一遍状态机扫描、内存内递归展开、两次写文件。性能碾压 noweb 的管道碎片化实现。

**语法约定**：文档块 Markdown 风格 + `$` 公式；chunk 定义 `<<name>>=` 独占一行（可选语言标注）；chunk 引用 `<<name>>`，代码态下行首才当引用（避免 C++ `cout << x` 误判）。需定死的规则：前导空白、名字字符集、行中定义、`$...$` 内 `<<` 豁免、转义约定。

**自举路线**：手写第一版 → 处理中等规模 `.nw` 验证 → 用第一版重写第一版 → 第二版用第一版生成，行为一致即自举完成。自举的真正收益是让工具成为自己规范的第一用户。

**结构组织**：顶层按章节组织（章节对应读者理解项目的路径，而非代码物理结构），章内 chunk 按叙事逻辑展开。每个 chunk 声明归属文件（`@file:`）和位置，tangle 时按文件聚合、按声明顺序拼接，拼出正常 repo 结构。**章节是阅读地图，目录树是产物形态。** 整个项目像一本书一样展开。

**分级视图**：语法提示、模式命名、领域前提按信息类型分组开关（非一维阶梯）；默认自适应（按 chunk 特征决定展开哪类）；关闭时留轻标记保留可发现性；IDE 交互式分级和 weave 静态分级分开处理。

**IDE 插件**（后续）：补全的触发权双向、修改可见性双向、chunk 边界可协商、叙事所有权共享。冲突解决原则：结构层面人优先，实现层面可协商（责任不对称——最终维护者是人）。

## 五、项目形态：一本书

项目本身就是用文学化编程写成的、可自举的文学作品。包含五项，成熟顺序不是并列的：

1. **语法规范**——最先定，本身用 `.nw` 写，是解析器实现依据、agent 提示词约束、自举测试依据三合一。
2. **理念说明**——问题陈述、核心判断、代价的诚实承认。让合适的人认出这是为自己做的。
3. **处理器**——parse + tangle + weave，用 `.nw` 写，最终自举。tangle 出的代码能编译，weave 出的文档就是说明书。
4. **Agent skill**——约束 agent 生成行为的技能包：读现有结构、只在 chunk 边界内修改、新增 chunk 必须写归属和位置、冒险写法必须附论证、语法糖必须附展开。
5. **IDE 插件**——交互式阅读和协作界面，工程复杂度最高，最后做。

**不发论文**：论文是外部描述，书是自我展开。项目 tangle 出工具、weave 出论证，读者读它就是在读论文、用工具、看实现，三件事在同一份源文件里发生。版本管理（git tag）替代论文的“发表版本”，引用一个 commit 比引用一篇论文更精确。代价是放弃学术渠道的传播和背书，靠读者自己读完后告诉别人。

**书的章节结构**：序章（问题陈述）→ 第一章（理念）→ 第二章（语法规范）→ 第三章（处理器）→ 第四章（人机协作）→ 第五章（IDE 插件）→ 第六章（实践）→ 附录（相关文献、对比、术语表）。

## 六、试水计划

用真实项目试水：composable infra simulation based on Kubernetes，规模较大。

**适合的原因**：组合式结构天然对应 chunk 引用图；理解难点在组件交互/时序/隐式契约，正是文档块价值最大的地方；AI 会大量参与胶水代码生成，正是屎山高发区。

**方法**：选一个中等复杂度组件（如调度器适配层或网络拓扑构建模块），用 `.nw` 写，观察三件事——chunk 粒度是否可控、weave 输出是否真的降低 review 成本、tangle + 编译 + 测试闭环是否顺畅接入现有构建系统。

**目的**：不是证明“处处适用”，是找到适用边界——哪些组件值得用 `.nw`、哪些阶段适合引入约束。检验的不是“工具能不能跑”，是“工具在真实工程节奏里能不能活下来”。

## 七、相关文献

- **notlob: A Literate Programming Environment for Human and Machine Agents**（arXiv:2608.24644，2026.08）——最接近。为人和机器 agent 共同构建文学化程序而设计环境；有语法、解析器、name-graph、`~test`/`~property` 标记；走“语言绑定”路线。代码仓库未找到。
- **VLP: Guiding Human Validation of LLM-Generated Code via Verifiable Literate Programming**（arXiv:2607.02333，2026.07）——用文学化文档作为可验证中间层，侧重审查-验证。
- **Literate Programming: Donald Knuth, WEB, and Contemporary Workflows**（Zenodo，Zhovten Games，2026）——提出 Prompt-Literate Workflow：人写 plan + chunk 契约 + 有界 prompt + 测试 + TRACE。非同行评审。配套仓库 `Zhovten-Games/literate-programming`。
- **The Fenced Block Principle**（DEV Community，2026.10）——每个代码块被意图声明“围栏”包围，配对关系可被 linter 检查，双栏 review 视图。
- **Literate Programming With LLMs?**（Sun & Staron, IEEE TSE 52(2):468-487, 2026）——正式同行评审，评估 LLM 的文学化编程能力，非工作流设计。
- **Natural Language Outlines for Code**（Google 等，FSE 2025）——用 LLM 生成自然语言大纲辅助人读代码，方向是呈现格式而非协作协议。
- Knuth, **Literate Programming**（The Computer Journal 27(2):97–111, 1984；书，1992）——奠基文献。

**判断**：思想层面已有同行者，工程实现层面仍然空旷——没有成熟工具把 chunk 结构、人机交替落笔、tangle/weave 闭环、IDE 内补全约束整合在一起。arXiv 上相关论文多为“思路描述 + 初步验证”。

## 八、一句话收束

这个项目把文学化编程从“个人写作方法”重新定位为**人机协作协议**和**信任基础设施**：让创作和审查发生在同一个文件、同一套结构里，同时降低创作难度、审查难度和理解成本；让 AI 承担它制造的理解成本；让跨栈项目的生产和教学在同一个结构里重合。它本身就是一本用文学化编程写成的书——论证不外在于被论证的东西，工具用自己的规范描述自己。
